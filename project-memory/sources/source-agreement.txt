**The plan has two separate layers:**

1. **The application pipeline:** turn your JD and canonical into a strong resume, cover letter, JSON and portable chat context.
2. **The development controls:** keep the coding agents within scope, make their work visible, and prevent repeated expensive guessing.

I inspected the current implementation before writing this. There are concrete defects to fix—not merely a need for more tests.

This explanation is the plan. **No new Markdown file, handoff or manual model switch.** Nothing below should be mistaken for functionality already completed.

**1. What is actually broken—and what changes first**

| Current problem I found | Why it matters | Planned correction |
|---|---|---|
| Writer receives fact/metric IDs without the corresponding evidence text | It cannot reliably turn the underlying work into specific writing | Resolve every reference into readable evidence before sending it |

**2. Layer one: the application’s data structure**

The YAML should describe your work. It should not contain the entire execution history, every generated resume, or every possible technology.

**Physical storage decision:** retain **one authoritative `canonical.yaml`** for now. Split it into typed, linked records internally. Creating dozens of competing YAML files would add migration work without fixing the missing evidence.

Three kinds of information remain separate:

| Information | Purpose | Changes when |
|---|---|---|
| **Canonical** | Your identity, employment, work, metrics and project pattern | You supply a factual correction or addition |
| **Policy** | Retrofit permission, writing preferences, structure and limits | You change a rule |
| **Application run** | A particular JD, decisions, selected work, writing and results | Each application |

A JD must never overwrite the canonical. A generated sentence must never quietly become a new canonical fact.

**Inside the canonical, the hierarchy is:**

```mermaid
flowchart TD
    C["Authoritative canonical"]
    C --> P["Profile and education"]
    C --> I["Professional identity"]
    C --> E["Employers"]
    C --> PP["Independent-project pattern"]

    E --> EM["Employer record<br/>Company, titles, dates, employment status"]
    EM --> S["System or initiative<br/>What was being built and why"]
    S --> N["Original narrative<br/>Keeps the surrounding meaning"]
    S --> F["Linked facts"]
    S --> M["Linked metrics"]
    S --> B["Linked boundaries"]
    S --> A["Distinct accomplishments"]

    F --> FP["Problem"]
    F --> FI["Inputs"]
    F --> FA["Actions"]
    F --> FO["Outputs"]
    F --> FR["Outcomes"]
    F --> FS["Implementation status"]

    A --> AR["References to compatible facts,<br/>metrics and boundaries"]
    AR --> EP["Resolved evidence packet"]
    N --> EP
    M --> EP
    B --> EP
```

**Each record has a specific job:**

| Record | What it contains | What it prevents |
|---|---|---|
| Employer | Stable ID, company, titles, dates | Changed companies or chronology |
| System | Problem, workflow narrative, linked records | Mixing unrelated initiatives |
| Problem fact | The operational problem | Bullets with no explanation of purpose |
| Input fact | Documents, events, records or other inputs | Vague descriptions of what the system handled |
| Action fact | What you built, changed or operated | Generic capability statements |
| Output fact | The resulting artifact or system behavior | Unsupported promises of impact |
| Outcome fact | What changed operationally | Confusing implementation with demonstrated impact |
| Metric | Value, meaning, scope, achieved/target status | Borrowing numbers from another project |
| Boundary | Ownership, deployment status or other qualification | Turning a prototype into a production claim |
| Accomplishment | A coherent, useful combination of those records | One bullet attempting to describe everything |
| Source reference | Original passage and stable reference | Losing the basis for a statement |
| Prototype pattern | Your authorized local/GitHub working pattern | Requiring an exhaustive project inventory |

**The split is semantic, not sentence-by-sentence.**

For example, “built a workflow that reads requests, validates them and creates approved records” may contain several actions, but those actions belong to one workflow. We preserve that connection.

We split separate achievements when they support genuinely different points: building the workflow, improving its operational behavior, and enabling adoption might justify different bullets. Merely renaming the same achievement does not.

**Most importantly: IDs are for Python. Actual evidence is for the model.**

For every potential bullet, Python assembles:

```text
Employer and system
Original system narrative
Selected problem and input facts
Selected action and output facts
Relevant outcome
Exact permitted metric, if any
Implementation status and boundaries
Assigned JD requirement
Functionally placed target technologies
The point this bullet must communicate
```

The writer and the corresponding Jev check receive that packet. They do not have to guess what `fact_17` means.

**4. How the JD is split without losing requirements**

```mermaid
flowchart TD
    RAW["Exact pasted JD"] --> SAVE["Save original text and input hash"]
    SAVE --> SEG["Python assigns passage IDs and source offsets"]
    SEG --> CHECK["Verify every nonblank source span is accounted for"]

    CHECK --> JC["Jev classifies passages<br/>Work, qualification, technology,<br/>company context, mixed or uncertain"]

    EX --> SP["Python checks quoted spans and IDs"]

    JC --> MERGE["Assemble complete JD brief"]
    JF --> MERGE
    RAW --> MERGE

    JF -->|Invalid or missing detail| FALL["Retain original passage<br/>Mark interpretation unresolved"]
    FALL --> MERGE

    MERGE --> MAP["Map actual work and plan application"]
```

Each requirement contains:

- Original passage.
- Plain-language interpretation.
- Priority.
- Child components.
- Named technologies.
- Any unresolved interpretation.

A requirement such as:

> Build applications that retrieve enterprise information, invoke tools and request approval before taking actions.

becomes meaningful components:

1. Retrieve enterprise information.
2. Invoke external tools or systems.
3. Enforce approval before the relevant action.

It does **not** become a separate requirement for every verb or noun.

**Failure behavior:** if the generated interpretation is incomplete, the original passage survives. We do not spend three drafts trying to achieve a perfect intermediate representation before writing anything.

However, retaining a passage does not magically prove coverage. An unresolved compound requirement remains visibly unresolved until its parts are accounted for.

**10. Page fitting and coverage must describe the same resume**

The final visible document is authoritative.

The sequence becomes:

1. Write the substantive draft.
2. Measure it using the renderer’s actual typography and flowables.
3. Preserve mandatory sections.
4. Select the strongest fitting experience content.
5. Render the preview.
6. Evaluate coverage against the content that actually remains.
7. Repair only if there is a localized reason.

Layout decisions consider **distinct useful coverage**, not merely the number of bullets.

The current exhaustive combination search will be replaced with a measured selection procedure that reuses block heights and avoids repeatedly rendering thousands of combinations. Final PDF pagination still verifies the result.

If a line-wrap boundary defeats the estimate, a bounded adjustment uses the actual rendered dimensions. It does not silently shrink the font.

**Specific rules:**

- Never remove the project to make fitting easy.
- Never remove an employer.
- Never shorten the letter to solve resume overflow.
- Never claim coverage from a removed bullet.
- Never pad the resume solely to occupy space.
- Never discard useful fitting material because an arbitrary global count was reached.

The coverage report distinguishes:

| Status | Meaning |
|---|---|
| Explicit | Final visible text clearly communicates the requirement |
| Partial | Only part of the requirement is expressed |
| Implied | Related work appears, but the requested capability is not explicit |
| Missing | No visible coverage |
| Uncertain | Interpretation or judgment remains unresolved |

It links to the actual sentence—not just a selected candidate ID.

- One JD extraction.

| Failure | Response |
|---|---|
| Missing source evidence | Fix the evidence assembly |
| Wrong skill group | Correct grouping; preserve unrelated prose |
| Misplaced technology | Correct that workflow placement |
| Generic wording | Rewrite the affected sentence using its evidence |
| Duplicate accomplishment | Replace or remove the weaker duplicate |
| Overflow | Adjust affected resume content only |

**14. Layer two: the harness around the coding agents**

The roles are deliberately narrow.

```mermaid
flowchart TD
    U["Your request and existing preferences"] --> A["Astra defines bounded change"]
    A --> C["Task contract<br/>Scope, required behavior, evidence,<br/>allowed changes and stopping conditions"]
    C --> CTRL["Python controller"]

    CTRL --> S["Sol implementation worker<br/>Fresh task context"]
    CTRL --> T["Optional Terra investigation<br/>Read-only, specific question"]

    S --> OUT["Diff, command results,<br/>artifact examples and failure details"]
    T --> OUT

    OUT --> PY["Python verification<br/>Scope, references, exit codes,<br/>budgets and artifact integrity"]
    OUT --> J["Jev requirement checks<br/>Satisfied, violated or insufficient evidence"]

    PY --> ROUTE["Controller routes result"]
    J --> ROUTE

    ROUTE -->|Supported completion| SAVE["Save result and advance"]
    ROUTE -->|Localized defect| FIX["One targeted worker correction"]
    FIX --> OUT
    ROUTE -->|Design conflict| ESC["Compact evidence packet to Astra"]
    ESC --> A
    ROUTE -->|Budget exhausted or repeated failure| STOP["Stop with preserved work"]
```

**Astra**

- Defines the task and resolves design conflicts.
- Does not repeatedly inspect unchanged logs.
- Does not perform routine implementation merely because it is the parent.
- Receives short evidence packets, not full worker transcripts.

**Sol**

- Implements the named task.
- Works from relevant files and a compact checkpoint.
- Cannot reinterpret settled requirements as optional.
- Cannot silently expand scope.
- Returns evidence, not “everything looks good.”

**Terra**

- Investigates a specific independent question when needed.
- Does not become mandatory overhead for every change.
- Does not duplicate Sol’s work.

**Python**

- Starts and stops workers.
- Captures events and commands.
- Checks allowed changes.
- Preserves reference criteria.
- Runs selected verification commands.
- Determines whether required evidence exists.
- Updates task state from results.

**Jev**

- Checks narrow semantic obligations.
- Does not execute commands.
- Does not authorize scope expansion.
- Does not replace mechanical verification.
- Does not certify arbitrary code correctness merely from a diff.

Automatic model selection removes the need for manual switching. More agents are not automatically better: initially, use one implementation worker at a time.

===== FOLLOW-UP EXPLANATION — VERBATIM =====

Your feedback gives us a clearer specification. **The accepted parts stay; the changes are page length, a clearer writing diagram, concrete observability choices, and small traceable commits.**

Also, the defects I found are a verified starting list—not a claim that we have found every problem.

**1. Resume length: content takes priority**

Your new rule replaces the previous one-page requirement:

- **One or two pages are acceptable.**
- A page and a half is acceptable.
- Keep the maximum of four bullets per employer.
- Keep relevant content rather than deleting it to achieve one page.
- Keep readable fonts and spacing.
- Prevent awkward breaks, such as an employer heading stranded at the bottom.

This removes the need for the complicated one-page subset selection.

If a resume unexpectedly reaches three pages, we first inspect formatting, duplication and unnecessarily long wording. **We do not silently delete useful accomplishments.** If it still exceeds two pages, preserve the draft and report the problem.

The existing code still enforces one page; changing the rule in this conversation has not yet changed that code.

---

**2. Your “blank paper with small writers” picture**

Your picture makes sense. It describes **separate writing units with their own responsibilities and checks**.

It differs from the previous proposal in one important respect:

> The proposal used one initial writing request to produce several separately identified blocks. It did not use an independent model call for every block.

These are two separate design choices:

| Choice | Meaning |
|---|---|
| **Separate ownership** | Each block has its own instructions, evidence, checks and revision history |
| **Separate model call** | Each block requires another request to the writing model |

We absolutely need separate ownership. We do not necessarily need a separate initial call for every block.

**My recommendation is: one coordinated initial draft, then independent block repairs.**

That gives the writer enough context to avoid repeating itself across employers, summary and letter. Afterwards, a bad bullet can be repaired without regenerating the rest.

This is a design recommendation—not a claim that we have already proved it produces better prose.

**Here is how the blank page gets filled:**

```mermaid
flowchart TD
    BRIEF["Complete application brief<br/>JD + resolved evidence + selected work<br/>skills + project + writing instructions"]

    BRIEF --> FIXED["Python copies fixed information<br/>Name, contact details, employers,<br/>titles, dates and education"]

    BRIEF --> SKILLS["Jev classifies individual skills<br/>Python assembles approved groups"]

    BRIEF --> WRITE["One initial writer request<br/>Returns separately identified text blocks"]

    WRITE --> SUM["Summary blocks<br/>Professional identity, relevant work and scope"]
    WRITE --> E1["Employer A blocks<br/>Up to four distinct accomplishments"]
    WRITE --> E2["Employer B blocks<br/>Up to four distinct accomplishments"]
    WRITE --> E3["Employer C blocks<br/>Up to four distinct accomplishments"]
    WRITE --> E4["Employer D blocks<br/>Up to four distinct accomplishments"]
    WRITE --> PROJ["Project blocks<br/>Local workflow, output and validation"]
    WRITE --> LETTER["Separate cover-letter blocks<br/>Opening, proof and closing"]

    FIXED --> PAGE["Python assembles the resume<br/>One or two pages"]
    SKILLS --> PAGE
    SUM --> PAGE
    E1 --> PAGE
    E2 --> PAGE
    E3 --> PAGE
    E4 --> PAGE
    PROJ --> PAGE

    LETTER --> LP["Python assembles the cover letter"]

    PAGE --> PREVIEW["Save JSON and draft PDF previews"]
    LP --> PREVIEW
    PREVIEW --> REVIEW["Run block, group and document checks"]
```

The writer does not position words on the PDF. It returns text attached to stable IDs. Python places those blocks in the template.

**Each writing unit has this information:**

| Field | Example purpose |
|---|---|
| Block ID | Identifies one particular bullet |
| Parent | Identifies its employer or section |
| Assigned point | What the block must communicate |
| Evidence | Actual source text, permitted metric and status |
| JD responsibility | The requirement it helps express |
| Technology placement | Which technology does what |
| Writing instruction | How to present the point clearly |
| Current text | The latest saved version |
| Check results | What passed, failed or remains uncertain |
| Revision history | What changed and why |

That is the modularity you want. A section’s rules can change without restructuring the entire pipeline.

**Here is the exact repair loop for one block:**

```mermaid
flowchart TD
    B["Saved bullet: employer B, bullet 2"]
    B --> J["Jev checks separate dimensions<br/>Clarity, assigned point, scope,<br/>evidence and technology placement"]

    J -->|Pass| KEEP["Keep this version"]
    J -->|Localized failure| ISSUE["Record exact failed dimension<br/>and required correction"]
    J -->|Insufficient evidence| DIAG["Inspect the input packet<br/>Do not guess or rewrite everything"]

    ISSUE --> W["Writer receives<br/>this block's evidence and instruction<br/>plus neighboring text as read-only context"]
    W --> PATCH["Return only the permitted block ID"]
    PATCH --> VALIDATE["Python rejects changes to other blocks"]
    VALIDATE --> RECHECK["Recheck changed bullet,<br/>affected employer and document dependencies"]
    RECHECK --> RESULT["Keep improved version<br/>or record unresolved issue"]

    RESULT --> LIMIT["Two shared repair rounds maximum<br/>No independent endless loop per block"]
```

**There is not a separately deployed Jev model for every box.** They are separate questions and records, sent through the same Jev API. Independent questions can share a request.

Similarly, repair writers can use the same writing model with different restricted inputs. We do not need eight different model configurations.

Your alternative—separate initial writers per section—remains a possible later experiment. We should change to it only if actual comparisons show that it improves the output. Otherwise, it adds coordination and requests without proven benefit.

**3. Observability: what exists and what we will use**

**Today:** there are saved requests, responses and run-state files. The full live observability setup is **not implemented**.

The concrete arrangement will be:

| Component | Selected approach | Responsibility |
|---|---|---|
| Execution | Existing Python pipeline | Runs the application stages |
| Data validation | Existing Pydantic models | Reject malformed records and events |
| Durable event record | Local append-only JSONL journal | Records what happened in order |
| Immediate live display | Python terminal display | Shows current stage, elapsed time, failures and artifacts |
| Trace exploration | Langfuse integration | Browse nested operations, inputs, outputs and evaluations |
| Coding-agent capture | `codex exec --json` | Captures the worker’s exposed execution events |
| Evaluation | Python checks plus Jev, run through the evaluation adapter | Measures behavior and output quality |

**LangChain is not required.** We do not need to rebuild the pipeline around it to get tracing.

**Pydantic is not the observability system.** It validates the structure of records.

**Langfuse is the trace viewer and analysis layer.** Its documented graph views can show either the overall workflow or individual calls, including repeated steps. [Langfuse graph documentation](https://langfuse.com/docs/observability/features/agent-graphs).

The local journal remains authoritative. The application must still run, show progress and retain evidence if Langfuse is unavailable. Trace export happens separately; it must not block resume generation.

Deployment of Langfuse is still a setup decision. I have not installed it or sent your data there.

**The two layers connect like this:**

```mermaid
flowchart TD
    subgraph DEV["Development timeline"]
        TASK["Task and requirement version"]
        AGENT["Worker model and session"]
        CMD["Commands and file changes"]
        CHECK["Verification and Jev judgments"]
        COMMIT["Git commit and result"]
        TASK --> AGENT --> CMD --> CHECK --> COMMIT
    end

    subgraph APP["Application timeline"]
        RUN["Application run"]
        JD["JD interpretation"]
        PLAN["Evidence, skills and project selection"]
        WRITE["Writing and block revisions"]
        EVAL["Hierarchical checks"]
        PDF["JSON, PDFs and context"]
        RUN --> JD --> PLAN --> WRITE --> EVAL --> PDF
    end

    COMMIT -->|"Application records its code version"| RUN

    DEV --> EVENTS["Local event journals<br/>Linked task, run, request and artifact IDs"]
    APP --> EVENTS

    EVENTS --> LIVE["Live terminal view"]
    EVENTS --> TRACE["Langfuse trace explorer"]
    EVENTS --> REPORT["Post-run report"]
```

**Live information**

You see:

- Which task or stage is active.
- Which model is actually running.
- Which request is outstanding.
- Time elapsed and its deadline.
- Whether work is cached, executing, failed or retrying.
- Which draft and evidence files are already available.
- Which block is being repaired and why.
- Stop/resume status.

**After completion**

You see:

- The exact code and input versions used.
- Where time was spent.
- What changed between drafts.
- What the checks approved or rejected.
- Which requirements appear in which final sentences.
- Why content was selected or omitted.
- Any unresolved issues.

For the coding agent, token usage is captured where the runtime exposes it. Subscription allowance remains an account-level measurement, not a precise per-command bill.

Codex’s non-interactive mode provides execution output suitable for scripted capture. That supports this setup, but does not expose every internal model operation. [Codex documentation](https://learn.chatgpt.com/docs/non-interactive-mode).

**For this existing chat:** I can report tools, file changes and decisions visible to me. I cannot retroactively create a complete trace of earlier inference or hidden reasoning. The proposed CLI controller makes future execution substantially more observable.

**4. Small commits: yes, that belongs in the design**

Your friend’s recommendation fits this project.

The rule will be **one coherent behavior change per commit**, rather than “commit after every arbitrary file edit.”

Examples:

- Permit two-page resumes without deleting content.
- Resolve evidence text in writer inputs.
- Remove unchecked technology-placement defaults.
- Calculate coverage from final visible text.

Those should be separate changes.

A commit message should explain:

```text
R6: Calculate coverage from final visible resume text

Problem:
Removed bullets were still counted as covering JD requirements.

Change:
Coverage now uses the selected, rendered application content.

Evidence:
Saved failing example: <case ID>
Focused verification: <result reference>

Scope:
No changes to source facts or writing prompts.
```

The commit already supplies an identifier and timestamp. The note supplies the **reason and evidence**.

The trace links together:

```text
Task ID → issue/example ID → code change → commit → application run
```

Additional rules:

- Preserve a starting checkpoint before implementation.
- Separate unrelated fixes.
- Label unfinished checkpoints honestly.
- Keep credentials and generated private application data out of Git.
- Reference local evidence without committing sensitive payloads.
- Use a PR for a reviewable group of changes when useful; committing locally does not require publishing a PR.
- Revert a specific faulty change when appropriate rather than rewriting history blindly.

I interpret your “temporal” point as preserving changes over time. **We do not need to introduce the Temporal workflow platform to achieve that.**

---

**5. Additional controls worth keeping**

Beyond tracing and commits, these four are particularly useful:

| Control | What it catches |
|---|---|
| **Input and configuration snapshots** | “Why did the same JD behave differently?” |
| **Prompt, rubric and model version tracking** | Changes caused by instructions or model configuration |
| **Before/after artifact comparison** | A code fix that accidentally worsens the resume |
| **Recorded-response replay** | Debugging deterministic code without repeatedly calling models |

These are small extensions of the execution record, not four new platforms.

The system must also distinguish **no progress** from **slow progress**. An active timer is not proof that useful work is happening. Repeated identical outputs, unchanged failures and exhausted repair budgets should produce an explicit stop.

---

**6. What you need to do**

You do **not** need to learn a special prompting language or protect the harness from ordinary conversation.

Normal messages should work:

| You say | The system should do |
|---|---|
| “This bullet is vague.” | Attach feedback to that bullet and diagnose it |
| “Allow two pages.” | Record a policy change and identify affected checks |
| “Why did it choose this project?” | Explain the saved selection; change nothing |
| “Try another summary.” | Create a revision while preserving the previous version |
| “Stop.” | Stop execution and save progress |
| “This needs a different architecture.” | Route a design change instead of quietly patching code |

You can include a run name or quote a sentence when convenient. If you do not, the interface should supply the current run or selected item.

When a message has multiple plausible meanings, the system should explain its interpretation before taking a consequential action. **It should not make you responsible for knowing its internal machinery.**

Your two-page instruction is a good example: it changes layout policy and associated checks. It does not authorize changing employers, rewriting the canonical or weakening content evaluation.

The reusable part for future pipelines is:

```text
    → observable execution
    → preserved artifacts
    → independently checked result
    → small versioned change
```

The resume-specific parts—canonical structure, skills taxonomy, writing criteria and project rules—remain separate modules.
